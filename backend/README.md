# Авторизация «Вместе»

[Спецификация MVP и архитектура проекта](https://gitlab.t-education.com/hack-ovb-02/specs/)

| Метод и путь | Запрос | Успешный ответ |
| --- | --- | --- |
| `POST /api/auth/register` | `email`, `nickname`, `password` | `201` с Bearer-токеном и созданным профилем |
| `POST /api/auth/login` | `email`, `password` | `200` с Bearer-токеном и профилем |
| `GET /api/auth/me` | Заголовок `Authorization: Bearer <accessToken>` | `200` с `id`, `email` и `nickname` текущего пользователя |
| `GET /api/users/{userId}/organizer-profile` | `organizerId` из карточки сбора. Токен необязателен. | `200` с `id`, `nickname`, `openGroupsCount` и `successfulGroupsCount` |

Регистрация и вход возвращают `accessToken`, `tokenType`, `expiresAt` и `user`. JWT действует один час. Для выхода клиент удаляет свою копию токена. При обновлении с предыдущей версии пользователи входят заново.

Почта сравнивается без учёта регистра. Пароль принимается длиной от 12 до 128 символов, ник — до 64. Некорректные поля дают `400`, неверные учётные данные — `401 INVALID_CREDENTIALS`, занятая почта — `409 EMAIL_ALREADY_EXISTS`. Для регистрации и входа действует общий лимит 20 запросов в минуту с одного IP.

## Каталог, сборы и личный кабинет

Миграции наполняют каталог четырьмя товарами. Поле `saleUnit` в товарах и сборах принимает `kilogram` для яблок и груш, `piece` для пачки кофе и банки мёда. Цены и лимиты указываются за одну такую единицу. При создании сбора, расчёте, прямой оплате и подтверждении лимита поле `quantity` задаёт количество. По умолчанию оно равно 1. Для штук допустимы целые числа, для килограммов — значения с точностью до грамма. В расчёте прямой оплаты `priceKopecks` — цена за единицу, `totalKopecks` — сумма за заказ. Подарок организатору имеет собственный объём.

| Метод и путь | Поведение |
| --- | --- |
| `GET /api/catalog/products?search=кофе` | Витрина с поиском по части названия без учёта регистра. Карточка содержит обычную цену, стартовую ступень и число открытых сборов. |
| `GET /api/catalog/products/{productId}` | Карточка товара со всеми ступенями, количеством и единицей измерения подарка в `organizerBonus` и списком открытых сборов. |
| `GET /api/groups` | Публичная лента сборов по лайкам организатора. Для порядка от новых к старым передайте `sortByOrganizerLikes=false`. Параметры `search`, `status`, `maxPriceKopecks`, `endsWithinHours` и `sortByOrganizerLikes` совместимы. Для активной ленты используйте `/api/groups?status=open&offset=0&limit=20`. |
| `POST /api/groups` | Создание сбора по JWT. Передайте `productId`, `deadline` и `organizerLimitKopecks` из ступени товара. Старое поле `targetParticipants` также выбирает личный максимум организатора. Каждый сбор сохраняет все ступени и подарок товара. Ответ `201` содержит код и ссылку-приглашение. |
| `GET /api/groups/{id}` | Публичная карточка сбора по его коду, в том числе после закрытия. |
| `POST /api/groups/{id}/join` | Вступление по Bearer-токену, тело запроса пустое. Тестовая оплата считается подтверждённой. Ответ `200` содержит актуальную карточку. Повтор сохраняет одно участие. Для нового участника закрытый сбор возвращает `409 GROUP_CLOSED`. |
| `GET /api/me/groups` | Мои открытые и завершённые сборы по JWT. Поле `myRole` принимает значение `organizer` или `participant`. Каждый сбор возвращается один раз. |

Лента возвращает массив карточек. По умолчанию `offset=0` и `limit=20`, допустимый размер страницы — от 1 до 100. Для следующей страницы увеличьте `offset` на `limit`. Страница короче `limit` означает конец списка. `regularPriceKopecks` — обычная цена в копейках, `priceTiers[].priceKopecks` — цена за единицу при достижении порога. Например, `99000` соответствует 990 ₽.

В Scalar (`/api/scalar/`) у каждого документированного ответа с ошибкой указан точный `title`. Например, `404 GROUP_NOT_FOUND` относится к сбору, а `404 PRODUCT_NOT_FOUND` — к товару. Для `400 VALIDATION_FAILED` подробности находятся в `errors`.

Публичный `id` нового сбора — восемь случайных букв и цифр, например `k7mp3v9x`. Один код используется в ссылке, при ручном вводе и в карточке товара. Регистр при поиске не важен. PostgreSQL хранит код в `group_purchases.invite_code` с уникальным индексом. Если при вставке код занят, сервер пробует другой. Первичный ключ и внешние ключи остаются UUID.

У ранее созданных сборов публичным `id` служит существующий 32-значный код приглашения. По старому UUID по-прежнему открывается `/api/groups/{uuid}`. Старые ссылки `/invite/{code}` и `/api/groups/invite/{code}`, поле `inviteCode` и списки `/api/account/organizing` и `/api/account/participating` сохранены для существующих клиентов.

Чтобы повторить создание после сетевого сбоя, передайте тот же заголовок `Idempotency-Key` и те же параметры. Ключ ограничен 128 символами и действует в пределах профиля организатора. Все цены передаются в копейках. Поле `deadline` в UTC используется для таймера. Сбор становится `successful` по самой дешёвой достижимой ступени. По каждой ступени суммируется заказанное количество. Порог в единицах товара доступен в `requiredQuantity`, оплаченный подходящий объём — в `eligibleQuantity`. Если к дедлайну сбор ещё `open`, его статус меняется на `cancelled`.

Для кнопки «Поделиться» фронтенд может собрать ссылку на свою страницу сбора по публичному коду `id` (он же `inviteCode`). Например, для маршрута `/groups/{code}` подойдёт `new URL("/groups/" + encodeURIComponent(group.id), window.location.origin).href`. Страница загружает карточку через `GET /api/groups/{code}`. Участник добавляется при вызове `POST /api/groups/{code}/join`.

Если ссылку формирует API, задайте `Invitations__UrlTemplate=https://web.example.test/groups/{code}` или `INVITATION_URL_TEMPLATE` в Docker Compose. API подставляет публичный код вместо `{code}` и разрешает запросы браузера с origin из шаблона. По умолчанию `inviteUrl` ведёт на JSON-карточку `/api/groups/{id}`.

Установите тестовую зависимость командой `python -m pip install websocket-client` и запустите `python tests/group_purchase_smoke.py`. По умолчанию тесты используют `http://127.0.0.1:5080`. Адрес можно задать в `API_BASE_URL`.

## «Куплю до…»

Маршруты используют публичный код сбора и Bearer JWT. Клиент передаёт сумму за одну единицу в целых копейках.

| Метод и путь | Поведение |
| --- | --- |
| `GET /api/groups/{id}/limit/quote?limitKopecks=99000` | Расчёт перед подтверждением. Возвращает доступность предоплаты, сумму списания и возврата при подтверждении, недостающий объём по личному лимиту и дедлайн. |
| `PUT /api/groups/{id}/limit` | Подтверждает или меняет заявку. Тело запроса содержит `limitKopecks`. |
| `GET /api/groups/{id}/limit` | Возвращает свою заявку и фактическое списание. |
| `DELETE /api/groups/{id}/limit` | Отзывает заявку до исполнения. |

Состояния заявки — `pending`, `purchased`, `revoked`, `closed`. При подтверждении списывается предоплата за всё количество. При успехе сбор создаёт один тестовый заказ на каждую подходящую заявку с ценой выбранной ступени и демонстрационным адресом доставки. По неподходящим и просроченным заявкам предоплата возвращается полностью. В `GET /api/me/groups` результат доступен в поле `myLimit`.

Если у сбора есть ожидающие или исполненные заявки, карточка включает соответствующие ненулевые счётчики `pendingLimitsCount` и `purchasedLimitsCount`. После успеха `settlementPriceKopecks` содержит итоговую цену. `eligibleParticipantsCount` показывает прогресс для `progressTier`. Для повтора `PUT` или `DELETE` передайте тот же `Idempotency-Key`. Для нового изменения нужен новый ключ.

## Тестовые карты и оплата

Все операции моделируются в PostgreSQL. Для карты достаточно четырёх цифр и внутреннего идентификатора. Все маршруты оплаты требуют Bearer JWT.

| Метод и путь | Поведение |
| --- | --- |
| `GET /api/me/cards` | Список активных тестовых карт. |
| `POST /api/me/cards` | Привязка тестовой карты. Тело содержит `lastFour`, например `"4242"`. Повтор возвращает тот же `id`. |
| `DELETE /api/me/cards/{cardId}` | Отвязка карты. Сохранённые заказы и ранее подтверждённые заявки сохраняют реквизиты. |
| `GET /api/groups/{id}/payment/quote` | Цена прямой оплаты, экономия, дедлайн и условие возврата. |
| `POST /api/groups/{id}/payment` | Подтверждение списания с кошелька. Передайте `confirmedPriceKopecks` из расчёта и `deliveryAddress`. `cardId` можно опустить. При росте цены возвращается `409 PRICE_CONFIRMATION_REQUIRED` с новым расчётом в `quote`. |
| `GET /api/groups/{id}/payment` | Свой заказ, списание и возврат. |
| `GET /api/me/payments` | История тестовых заказов и суммарное изменение средств в копейках. |

Для повтора подтверждения передайте тот же `Idempotency-Key` и те же параметры. `POST /join` тоже списывает с кошелька и использует демонстрационный адрес. При создании сбора можно передать `cardId`, `deliveryAddress` и `confirmedPriceKopecks`. Для «Куплю до…» можно передать `cardId` и `deliveryAddress` вместе с лимитом.

При успехе каждый заказ получает общую цену за единицу. Для прямой оплаты в `myPayment.paidKopecks` хранится исходное списание, в `myPayment.refundedKopecks` — возвращённая разница за весь заказ. По дедлайну открытого сбора сервер возвращает её полностью. В `GET /api/me/groups` личный денежный результат доступен в `myPayment`. Старые прямые участия без записи об оплате сохраняются в составе сбора.

При создании с личным лимитом организатора успешный сбор начисляет подарок из карточки товара. Его количество и единица видны в `myBonus`, даже если итоговая цена выше личного лимита. При создании сбора организатор выбирает одну из ценовых ступеней товара.

## Тестовый кошелёк

Оба маршрута требуют Bearer JWT и работают с кошельком текущего пользователя.

| Метод и путь | Поведение |
| --- | --- |
| `GET /api/me/balance` | Остаток `balanceKopecks` и суммы пополнений, списаний кошелька, возвратов, кэшбэка и реферальных бонусов в копейках. |
| `POST /api/me/balance/top-ups` | Тестовое пополнение. Передайте `{"amountKopecks": 100000}` и `Idempotency-Key`. Допустимая сумма от 1 до 100 000 000 копеек. Повтор с тем же ключом и суммой возвращает прежнее пополнение. |

Для новой заявки «Куплю до…» и покупки организатора обязательна предоплата по цене выбранной ступени за весь заказ. Недостаток средств возвращает `409 INSUFFICIENT_BALANCE`, неизвестная ступень — `400 PRICE_TIER_UNAVAILABLE` в ошибках поля. Изменение количества или лимита списывает или возвращает разницу. При исполнении по более низкой цене сервер возвращает переплату, при отзыве или закрытии без покупки — всю предоплату. В личной заявке `chargedKopecks` показывает чистую сумму, `refundedKopecks` — накопленные возвраты, `remainingQuantity` — сколько товара не хватает до подходящей цены. Заявки, подтверждённые до перехода на предоплату, сохраняют прежнее согласие на оплату при исполнении. Новая предоплата по ним возникает при подтверждении изменений.

Отмена возвращает деньги на тот же тестовый источник, с которого проведено списание. Карточные операции и заявки, оформленные до миграции, продолжают учитываться по прежней схеме. Накопленные кэшбэк и реферальные начисления доступны в кошельке. `netChangeKopecks` в истории оплаты отражает итог операций по заказам и бонусам.

## Уведомления о покупке и возврате

Оба маршрута требуют Bearer JWT. Фронтенд может обновлять ленту при открытии личного кабинета и периодически опрашивать API.

| Метод и путь | Поведение |
| --- | --- |
| `GET /api/me/notifications?offset=0&limit=20&unreadOnly=true` | Свои уведомления, сначала новые. По умолчанию возвращаются и прочитанные. Допустимый размер страницы — от 1 до 100. |
| `PUT /api/me/notifications/{notificationId}/read` | Отметить уведомление прочитанным. Повтор сохраняет дату прочтения и возвращает `204`. Для неизвестного или чужого уведомления возвращается `404 NOTIFICATION_NOT_FOUND`. |

Элемент содержит `id`, `kind`, публичный код `groupId`, `productId`, `productName`, `amountKopecks`, `createdAt` и `readAt`. У непрочитанного уведомления `readAt` равен `null`.

Уведомление `purchase` появляется у владельца заказа после успешного завершения сбора. Сумма — фактическая цена заказа, включая 0 ₽ за бесплатную единицу. При отмене после возврата платежа появляется `refund` с полной суммой возврата. Для старых завершённых заказов без времени завершения используется время начисления подарка или оплаты.

Публичный список участников доступен через `GET /api/groups/{id}/participants?offset=0&limit=20`. Для каждого участника возвращаются только `userId` и `nickname`. Отозванные заявки исключаются.

## Чат сбора

Читать чат могут все посетители. Писать могут организатор и участники с действующей покупкой или заявкой, в том числе после закрытия сбора. Сообщения сохраняются в PostgreSQL.

Подключайтесь по `wss://<host>/api/groups/{id}/chat/ws`. Сервер присылает `{"type":"ready","data":[...]}` с последними 50 сообщениями. При переподключении передайте `?afterId=<последний id>`, чтобы получить пропущенные сообщения по порядку. Для пустой истории можно использовать `afterId=0`.

| Кадр клиента | Ответ сервера |
| --- | --- |
| `{"type":"auth","accessToken":"<JWT>"}` | `{"type":"authenticated"}`. Для отправки сообщений дождитесь этого ответа. |
| `{"type":"message","text":"Сообщение","idempotencyKey":"..."}` | `{"type":"sent","data":{...}}` подтверждает сохранение и возвращает то же сообщение при повторе с тем же ключом. |
| `{"type":"history","beforeId":123,"limit":50}` | `{"type":"history","data":[...]}`. Также поддерживается `afterId`. |
| `{"type":"ping"}` | `{"type":"pong"}` |

Все подключённые к сбору клиенты, включая отправителя, получают новые сообщения в событиях `{"type":"message","data":{...}}`. Используйте `id` для объединения истории, подтверждений и событий. Ошибки приходят как `{"type":"error","title":"...","status":400}`. Лимит отправки — 20 сообщений в минуту на аккаунт. Максимальная длина сообщения — 1000 символов.

## Лайки организаторам

Профиль `GET /api/users/{userId}/organizer-profile` возвращает `likesCount` и `likedByMe`. С Bearer-токеном `likedByMe` показывает состояние лайка текущего пользователя.

| Метод и путь | Поведение |
| --- | --- |
| `PUT /api/users/{userId}/organizer-profile/like` | Поставить один лайк. Повтор возвращает профиль с тем же числом лайков. Для своего профиля возвращается `409 CANNOT_LIKE_SELF`. |
| `DELETE /api/users/{userId}/organizer-profile/like` | Снять свой лайк. Повтор также возвращает профиль. |

Обе операции требуют Bearer-токен и принимают пустое тело. Лайк принадлежит организатору и учитывается во всех его сборах. Поле `organizerLikesCount` доступно в карточках сборов.

В карточке товара и в `GET /api/groups` по умолчанию выше сборы организаторов с большим числом лайков, затем с ближайшим дедлайном. При равенстве порядок определяется идентификатором. Витрина показывает товары по названию. Для клиентов каталога также доступен `GET /api/catalog/products?sortByOrganizerLikes=true`. Этот режим работает вместе с `search` и сортирует по лайкам самого популярного организатора среди открытых сборов каждого товара. Товары без открытых сборов идут в конце, у них `topOrganizerLikesCount` равен `null`. При одинаковом рейтинге товары упорядочиваются по названию и идентификатору.

## Изображения товаров

Команда `docker compose up --build -d` поднимает MinIO и запускает `minio-init`. Инициализация создаёт бакет `catalog`, загружает фотографии из `infra/minio/products/` и разрешает анонимное чтение объектов под `products/`. Изображения сохраняются в томе `minio-data`.

В PostgreSQL хранится ключ объекта в `products.image_key`. API собирает из него абсолютный `imageUrl`, который можно передать в `<img src>`. Для локального Compose получается `http://localhost:9000/catalog/products/coffee-cerrado.webp`. Для удалённого браузера задайте публичный адрес бакета в `MINIO_PUBLIC_BUCKET_URL` или, при запуске API вне Compose, в `Storage__PublicBucketUrl`. У товара без ключа `imageUrl` равен `null`.
